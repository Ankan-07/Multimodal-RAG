# Multimodal RAG — Architecture Analysis, Bottlenecks & Scaling Roadmap

> **Scope**: This document describes the current implementation as of
> November 2026. Every claim is grounded in the source files in this
> repository. Measured timings are marked as measurements taken on the
> developer machine.

---

## 1. Current Architecture

The system is a **hybrid retrieval RAG pipeline**. Text chunks are embedded
locally with a Sentence Transformer. Images and tables are embedded with
Google Gemini Embedding 2. BM25 adds keyword and number matching. The three
ranked lists are merged with Reciprocal Rank Fusion (RRF) and the answer is
generated by a vision-capable model through OpenRouter.

### 1.1 High-Level Pipeline

```
INGESTION (index-time)
  PDF file
    -> partition_document()        # unstructured hi_res, table + image extraction
    -> create_chunks_by_title()     # title-boundary chunking (max 3000 chars)
    -> per chunk: separate_content_types()
         text    -> TextRecord    (raw chunk text)
         image   -> VisualRecord   (image bytes, kind="image")
         table   -> VisualRecord   (table text, kind="table")
    -> store (HybridVectorStore)
         text_chunks_minilm  (MiniLM, 384-d, cosine)
         visual_chunks_gemini (Gemini, 768-d, cosine)
         BM25L index over text chunks and table text

QUERY (query-time)
  User query
    -> MiniLM text query (top 5)
    -> Gemini visual query (top 5)
    -> BM25 query (top 5)
    -> RRF fusion (k = 60)
    -> merge by chunk_id (scores sum), cap at 5 chunks
    -> generate_final_answer()
         ChatOpenAI(model="openrouter/free") via OpenRouter
         text prompt + table HTML + up to 3 images (base64 data URLs)
    -> Answer + Source panel in Streamlit UI
```

### 1.2 Module Map

| File | Role | Stage |
|---|---|---|
| `document_processor.py` | PDF partition, title chunking, content type separation | Extract |
| `ingestion.py` | Build text/image/table records from one PDF | Transform |
| `records.py` | `TextRecord`, `VisualRecord`, `IngestionBatch` dataclasses | Types |
| `gemini_embeddings.py` | Gemini Embedding 2 client (text + image, retry with backoff) | Embed |
| `bm25_store.py` | `BM25L` keyword index (tokenizer handles numbers) | Index |
| `vector_store.py` | `HybridVectorStore`: two Chroma collections + BM25 + context lookup | Store |
| `retriever.py` | Hybrid retrieval, RRF, answer generation, UI source extraction | Retrieve + Generate |
| `pipeline.py` | CLI orchestrator (ingest + query) | Entry point |
| `app.py` | Streamlit UI | Frontend |
| `config.py` | All constants (models, paths, caps, top-k) | Cross-cutting |

### 1.3 Key Design Strengths

- **Direct multimodal embedding.** Images are embedded as image bytes
  (`gemini_embeddings.py::embed_image_bytes`); tables are embedded as their
  normalized text (`embed_text`). The old "generate a searchable summary with
  a VLM, then embed the summary" approach has been removed.
- **Separate vector spaces.** Two Chroma collections with cosine HNSW
  (`vector_store.py::__init__`), because MiniLM (384-d) and Gemini (768-d)
  vectors are not comparable.
- **Deterministic record IDs.** `ingestion.py::_chunk_id` is a SHA-1 over
  `source|page|index|text`, so re-ingestion upserts the same IDs instead of
  duplicating records.
- **Context stored once per chunk.** The `original_content` JSON (raw text,
  table HTML, base64 images, MIME types, source, page) is attached only to the
  first record of a chunk; other records store only `chunk_id` and resolve the
  context through `vector_store.get_chunk_context`. This avoids duplicating
  large base64 blobs per image/table record.
- **Image hygiene.** Images under 100×100 are dropped; duplicates inside one
  chunk are dropped; unsupported formats are converted to PNG
  (`ingestion.py::_prepare_image`).
- **Lazy Gemini client.** The visual embedder is created only on first use
  (`vector_store.py::visual_embedder` property), so a text-only store opens
  without a `GEMINI_API_KEY`.
- **Resilient embedding calls.** Transient failures (HTTP 408/429/500/502/503/504
  and network errors) are retried with exponential backoff (1s → 16s cap);
  permanent errors fail loudly (`gemini_embeddings.py`).
- **RRF across incomparable scores.** Raw cosine scores from MiniLM and Gemini
  are not directly comparable; RRF uses only ranks (`retriever.py::_rrf_fuse`).
- **Chunk-level merge.** Records from all three sources are merged by
  `chunk_id` and their RRF scores are summed, so a chunk found by multiple
  sources ranks above one found by a single source
  (`retriever.py::_merge_by_chunk`).

## 3. Bottleneck Catalogue — Current Implementation

### 3.1 Visual Embedding Is Serial and Slow  ⚠️ Critical

**Where**: `vector_store.py → add_visual_records()` — a plain `for` loop over
records, each calling the Gemini API (image bytes or table text).

**Problem**: Every image and every table is one separate Gemini embedding
request, sent one after another. Measurements on 2026-11-24 (developer
machine, JEPA paper):

- 34 text records + 93 visual records were built from one PDF.
- Adding the batch (mostly the 93 Gemini embeddings) took **~320 seconds**
  (~3.4 s per visual record on average).
- The Streamlit "Process Documents" run for the same PDF (partition + embed)
  completed in **~231 seconds**; the batch-add step dominated that time.

There is no concurrency and no batching. Under a per-minute API rate limit,
the retry-with-backoff path makes this even slower.

### 3.2 PDF Partitioning Is Single-Threaded and CPU/GPU Bound  ⚠️ Critical

**Where**: `document_processor.py → partition_document()`.

**Problem**: `unstructured`'s `hi_res` strategy loads layout/OCR models and
runs page-by-page. `app.py` loops over uploaded files sequentially:

```python
# app.py, "Process Documents" handler
for uploaded_file in uploaded_files:
    batch = build_ingestion_records(temp_path)   # blocking, sequential
```

Five PDFs means five fully sequential partition passes.

### 3.3 Base64 Images Stored Inside ChromaDB Metadata  ⚠️ High

**Where**: `vector_store.py` metadata; `ingestion.py::_build_original_content`.

**Problem**: The answer-time context (raw text, table HTML, base64 images)
is serialized into one JSON string and stored in Chroma metadata. This is now
**mitigated**: the context is written only once per chunk (first record), and
images are deduplicated within a chunk. Still, a chunk with several images can
carry hundreds of KB of base64 in metadata, which is not what a vector DB's
metadata layer is designed for (write amplification, memory pressure, query
overhead).

### 3.4 Embedding Model Cold Start + Online Hub Check  ⚠️ Medium

**Where**: `vector_store.py` constructs `HuggingFaceEmbeddings` (from
`langchain-huggingface`) at store creation; `app.py` opens the store once per
process.

**Problem**: `sentence-transformers` performs an online reachability check
against `huggingface.co` even when the model is cached locally. On a flaky
network this retries with exponential backoff before falling back to cache.
Measured cold start on the developer machine:

- Default: **~23.6 s** (including the failed online check and retries).
- With `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` in `.env`:
  **~13.1 s**.

The remaining ~13 s is PyTorch import + model load, paid once per server
process. Note: the offline flags are set in the local `.env` (gitignored);
a fresh clone will not have them unless the user adds them.

### 3.5 Answer LLM Client Created Per Question  ⚠️ Medium

**Where**: `retriever.py → generate_final_answer()` — `ChatOpenAI(...)` is
constructed inside the function on every question.

**Problem**: The HTTP client (httpx) is created, configured, and torn down
for every chat question. This defeats connection pooling across questions and
adds TLS handshake overhead per question. (It is not per-chunk: the loop
builds the prompt and then makes one LLM call per question.)

### 3.6 No Re-Ranking / Query Optimization  ⚠️ Medium

**Where**: `retriever.py → retrieve_documents()`.

**Problem**: Each source returns a flat top-5; RRF fuses ranks. There is no
cross-encoder reranker, no query expansion, no HyDE, and no MMR. A false
positive in any source's top-5 can enter the final top-5 directly.

### 3.7 No Cross-Session Checkpointing  ⚠️ Medium

**Where**: `app.py`, `pipeline.py`, `vector_store.py`.

**Problem**: Ingestion of one document is not check-pointed. If the process
dies mid-batch (e.g., after 40 of 93 Gemini calls), the work is lost and the
user must re-run. Re-running is safe (deterministic IDs + `delete_source` +
upsert), but there is no resume-within-batch. Per-record failures are counted
and warned, and a total visual failure raises a `RuntimeError` (so a missing
key cannot masquerade as success).

### 3.8 Free-Tier Model Routing Is a Single Point of Failure  ⚠️ Structural

**Where**: `config.py` — `ANSWER_MODEL = "openrouter/free"`.

**Problem**: OpenRouter's `openrouter/free` router selects among free models;
free endpoints have unpredictable availability, rate limits, and output
quality, and can be removed without notice. The answer path has no fallback
chain if the selected free model errors. The Gemini Developer API key is also
a single dependency for all visual functionality.

handle hundreds of documents / millions of chunks without code rewrites.

## 5. Bottleneck-by-Bottleneck Solutions

### 5.1 Parallelize Visual Embedding

**Solution**: Replace the serial `for` loop in `add_visual_records` with a
bounded `ThreadPoolExecutor` (IO-bound API calls) or asyncio. Respect the API
rate limit (HTTP 429) with a semaphore and the existing retry/backoff.

```python
# vector_store.py — sketch
from concurrent.futures import ThreadPoolExecutor

def add_visual_records(self, records):
    with ThreadPoolExecutor(max_workers=8) as pool:
        results = list(pool.map(self._embed_one_visual, records))
    # upsert successes, count failures
```

**Expected gain**: 3–10× throughput, bounded by the API's concurrent rate
limit rather than by latency.

### 5.2 Parallelise PDF Partitioning

**Solution**: Use `ProcessPoolExecutor` (not threads — GIL-bound OCR is
CPU-heavy) to partition multiple PDFs concurrently, up to `os.cpu_count()`
workers.

```python
# pipeline.py — sketch
from concurrent.futures import ProcessPoolExecutor

def ingest_multiple_pdfs(pdf_paths):
    with ProcessPoolExecutor(max_workers=os.cpu_count()) as pool:
        return list(pool.map(build_ingestion_records, pdf_paths))
```

For single very large PDFs, consider splitting the PDF at the page level
(using `pypdf`) and partitioning page-batches in parallel, then merging.

### 5.3 Move Images Out of ChromaDB Metadata

**Solution**: Extract images to a content-addressed object store keyed by
SHA-256 hash of the image bytes. Store only the key in Chroma metadata.

```python
# image_store.py — sketch
import hashlib, os

IMAGE_DIR = "content/images"  # swap for S3 bucket at scale

def store_image(image_base64: str) -> str:
    """Returns a stable key; deduplicates identical images."""
    img_bytes = base64.b64decode(image_base64)
    key = hashlib.sha256(img_bytes).hexdigest() + ".jpg"
    path = os.path.join(IMAGE_DIR, key)
    if not os.path.exists(path):
        with open(path, "wb") as f:
            f.write(img_bytes)
    return key

def load_image(key: str) -> str:
    """Returns base64 on demand."""
    with open(os.path.join(IMAGE_DIR, key), "rb") as f:
        return base64.b64encode(f.read()).decode()
```

Metadata stored in Chroma becomes:

```json
{
  "raw_text": "...",
  "tables_html": ["<table>..."],
  "image_keys": ["a3f9...jpg", "b2e1...jpg"]
}
```

**Impact**: Chroma metadata shrinks from ~200 KB/chunk (with images) to ~2 KB.

### 5.4 Warm Embedding Model + Offline Mode

**Solution**: Keep the current `@st.cache_resource` store (already
implemented) and set `HF_HUB_OFFLINE=1` + `TRANSFORMERS_OFFLINE=1` in the
environment (currently only in the local `.env`). Consider documenting these
in `.env.example` so fresh clones get fast startup too. If a future embedder
upgrade is needed, batch embedding (`batch_size=64`) over the full corpus at
index time is recommended.

### 5.5 Persist and Reload Vector Store in Streamlit — ✅ DONE

Already implemented: `app.py::_open_store` uses `@st.cache_resource` and
`HybridVectorStore` opens the persisted `dbv3/chroma_db`; BM25 is rebuilt from
persisted records on open. Refreshing the browser or restarting the server
resumes the same index.

### 5.6 Add a Re-ranking Stage

**Solution**: Retrieve top-20 with the bi-encoder, then score and re-rank with
a cross-encoder.

```python
# retriever.py — sketch
from sentence_transformers import CrossEncoder

_RERANKER = CrossEncoder("BAAI/bge-reranker-v2-m3")

def rerank(candidates, query, top_k=5):
    pairs = [(query, c["document"]) for c in candidates]
    scores = _RERANKER.predict(pairs)
    ranked = sorted(zip(scores, candidates), key=lambda x: x[0], reverse=True)
    return [c for _, c in ranked[:top_k]]
```

**Recommended model**: `BAAI/bge-reranker-v2-m3` — multilingual, ~280 MB,
runs on CPU in ~50 ms for 20 candidates.

### 5.7 Hybrid Retrieval (Dense + BM25) — ✅ DONE

Already implemented: text vectors + Gemini visual vectors + BM25L, fused with
RRF in `retriever.py`. Any further work should focus on tuning `k` per source
and adding the reranker, not on adding BM25.

### 5.8 Checkpoint-Based Ingestion (Idempotency)

**Solution**: Track ingestion progress in a lightweight SQLite/JSON state file
keyed by `(doc_id, record_id)`. On failure/restart, skip already-completed
records. Re-ingestion is already safe (deterministic IDs + upsert), so the
checkpoint only saves time, not correctness.

### 5.9 LLM Fallback Chain

**Solution**: Define a priority list of models with automatic fallback on
error/timeout, and hoist the client to module level so the connection pool is
reused across questions.

```python
# llm_gateway.py — sketch
from langchain_openai import ChatOpenAI

MODEL_CHAIN = [
    {"model": "anthropic/claude-sonnet-4-6", "base_url": config.OPENROUTER_BASE_URL},
    {"model": "openrouter/free", "base_url": config.OPENROUTER_BASE_URL},
]

_LLM = None

def get_llm():
    global _LLM
    if _LLM is None:
        _LLM = ChatOpenAI(
            model=config.ANSWER_MODEL,
            base_url=config.OPENROUTER_BASE_URL,
            temperature=0,
        )
    return _LLM
```

### 5.10 Upgrade the Embedding Model

**Current**: `all-MiniLM-L6-v2` — 384-dim, English-optimised, 22M params,
~90 MB.

**Problem at scale**: 384 dimensions cause HNSW recall to degrade as the
collection grows past ~100K chunks. English-only fails on multilingual
documents.

**Recommended upgrade path**:

| Model | Dims | Size | Notes |
|---|---|---|---|
| `BAAI/bge-small-en-v1.5` | 384 | 130 MB | Better than MiniLM on BEIR benchmarks, same speed |
| `BAAI/bge-base-en-v1.5` | 768 | 430 MB | Significant quality jump, ~2× slower |
| `BAAI/bge-m3` | 1024 | 570 MB | Multilingual, dense+sparse+multi-vector, best quality |
| `text-embedding-3-small` | 1536 | API | No local inference |

Visual embedding would still use Gemini Embedding 2.

## 6. Queue-Based Architecture for True Scale

For production ingestion of hundreds of documents per day, a synchronous
pipeline inside Streamlit is unacceptable. The correct model is **background
job processing**.

```
┌─────────────────┐      HTTP POST /ingest      ┌────────────────────┐
│  Frontend/API   │ ─────────────────────────▶ │  FastAPI Backend   │
│  (Streamlit /   │                             │  (stateless)       │
│   REST client)  │ ◀─────── job_id ──────────  └────────┬───────────┘
└─────────────────┘                                      │ enqueue
                                                          ▼
                                               ┌────────────────────┐
                                               │  Redis / RabbitMQ  │
                                               │  Task Queue        │
                                               └────────┬───────────┘
                                                        │ dequeue
                            ┌───────────────────────────┼──────────────────────────┐
                            │                           │                          │
```

## 9. Summary

The current architecture is a hybrid, multimodal RAG system:

- **Ingestion**: unstructured `hi_res` partition → title chunking → three
  record types (text / image / table) → two Chroma collections (MiniLM 384-d,
  Gemini 768-d) + a BM25L keyword index.
- **Retrieval**: three sources (text vectors, visual vectors, BM25) → RRF →
  chunk-level merge → top-5 chunks.
- **Generation**: OpenRouter `openrouter/free` vision-capable model receives
  raw text, table HTML, and up to three images.

Main risks for scale:

1. **Serial Gemini embedding calls** per visual record (measured ~3.4 s each;
   ~320 s for a 93-visual PDF) — fix with bounded concurrency.
2. **Binary blobs in vector DB metadata** — mitigated by once-per-chunk
   storage; fix fully with a separate image store.
3. **Single-process, synchronous everything** — fix with background workers and
   a persistent vector DB like Qdrant.
4. **No re-ranking** — fix with a cross-encoder, the highest-ROI retrieval
   quality improvement.
5. **No resilience** — free-tier `openrouter/free` routing has no fallback;
   add retry/fallback chains and checkpoint-based ingestion.

The modular codebase structure makes all of these improvements surgical — each
module has a single responsibility and can be upgraded independently without
touching the others.
